The biggest size reduction in the toolbox

This conversion pairs the least efficient common format with one of the most efficient. BMP writes every pixel uncompressed, roughly three bytes per pixel at 24-bit colour, whatever the image contains. WebP applies a modern codec that is itself 25-35% more efficient than JPEG. The gap between them is enormous: reductions of 95% or more are routine rather than exceptional. In our own testing a 28 KB test bitmap encoded to just over 400 bytes as WebP.

If you are handling BMP output from a scanner, an instrument or an older Windows application and the destination is a website, WebP is very likely the right target. It is the format that makes those files behave like normal web assets.

Lossy or lossless: this one is a real decision

WebP supports both, and the choice depends entirely on what the bitmap contains. For photographs, use lossy WebP: it is what the format is optimised for, the quality loss is not visible at sensible settings, and the file will be a tiny fraction of the original. For screenshots, diagrams, scanned text and flat graphics, consider lossless WebP: it still compresses roughly 26% better than PNG on that kind of content, and lossy compression can smear the hard edges of text and UI elements in a way that is immediately noticeable.

Transparency is supported in both modes, though BMP itself rarely carries an alpha channel, so this usually only matters if you are compositing afterwards.

Getting the target size you need

Because the source is uncompressed, the quality slider has an unusually wide range of useful settings, almost anything you pick will be dramatically smaller than the BMP. If you have a specific budget in mind, set a KB ceiling instead and let the encoder search for the best quality that fits under it. That is more reliable than guessing, since a quality number produces very different file sizes depending on how much detail the image holds.

Resize while you are at it

BMPs from scanners and instruments are frequently far larger in pixel terms than anything you will display. Reducing the dimensions is the strongest single lever on file size, halving width and height removes three quarters of the pixels before compression begins. Set a resize alongside the format change and both are applied in one pass.

Batch conversion, entirely local

Uncompressed files are big, so batches add up fast. Drop up to 200 BMPs and each is decoded and encoded independently, with results available individually or as a single ZIP. Nothing is uploaded: there is no transfer time for those large originals and no server-imposed size cap, because the encoders are WebAssembly builds running in your own browser tab.

That also means it works offline once the page has loaded, and that scanned paperwork or internal captures never reach a third party. Open the Network panel in developer tools while a batch runs and you will see no image traffic at all.

Frequently asked questions

How much smaller is WebP than BMP?

Typically 95% or more, because BMP applies no compression while WebP uses a modern codec. In our testing a 28 KB test bitmap encoded to just over 400 bytes as WebP. This is the largest reduction the tool routinely produces.

Should I choose lossy or lossless WebP?

Lossy for photographs: that is what the format is optimised for and the loss is not visible at sensible quality. Lossless for screenshots, diagrams and scanned text, where lossy compression can smear hard edges; lossless WebP still beats PNG by roughly 26% on that kind of content.

Is WebP safe to use on a website?

Yes. WebP is supported by effectively every current browser, and has been for years. For non-browser destinations such as email, print or older desktop software, JPG or PNG remains the safer choice.

Can I hit a specific file size?

Yes. Set a KB ceiling and the encoder searches quality until the output fits at or under it, rather than you guessing a quality number. This is more reliable because the same quality setting produces very different sizes depending on image content.

Should I resize as well as convert?

Often yes. Bitmaps from scanners and instruments are frequently much larger in pixel terms than needed. Halving width and height removes three quarters of the pixels before compression, so resizing is the strongest lever on final size, and it can be applied in the same pass.

Do my files get uploaded?

No. Everything is decoded and encoded inside your browser using WebAssembly, so there is no transfer time and no server size limit. You can verify it by watching the Network tab in developer tools during a conversion.
